# Immich Fork Development

## 目标

在尽量不偏离上游的前提下，优化元数据提取及任务队列，并按实际需求扩展服务端与少量 Web 管理能力。本 Skill 是开发工作流，仓库根目录 `AGENTS.md` 是必须遵守的工程边界。运行环境与上游版本必须从当前仓库和实际部署核实，不能使用过期假设。

## 每次任务的执行顺序

1. **收敛需求**：确认当前要解决的一个用户可观察问题、验收标准和不修改的范围；不要把功能修复扩大为架构重写。
2. **读取现状**：阅读目标目录代码、对应测试、`AGENTS.md`、`CONTRIBUTING.md` 和相关配置。找到真实入口、依赖、任务生命周期与上游已提供的机制；确认基线版本及与上游的差异。
3. **判断变更边界**：
   - 纯服务端业务/性能：优先改 `server/`。
   - 需要显示队列状态、耗时、错误或管理入口：允许最小范围修改 `web/`，必要时新增独立且鉴权正确的管理 API。
   - 官方 iOS/Android 客户端：不改 `mobile/`；不破坏已有 API、用户登录、资源读取及照片同步语义。
4. **先建立证据**：对性能类任务在修改前保存可以复现的基线；对正确性类任务先明确失败案例与不变量。
5. **实现最小补丁**：尽量复用原有仓库与依赖，修改生成源而非手改 SDK 生成结果。若 API 必须改变，先给出兼容性影响与客户端验证路径，不隐式改变现有接口含义。
6. **分层验证**：先跑变更关联的单测、静态检查，再跑隔离环境集成验证；仅在需要时扩大到全量测试与镜像构建。测试失败时如实记录。
7. **交付与回退**：输出改动点、数据、风险、上游合并冲突概率及可回退方式。合并 `main` 与发布镜像需经过独立验证；开发镜像不能自动替换生产实例。

## 元数据提取性能专项

优先定位 `server/src/repositories/metadata.repository.ts` 及其上层任务创建、消费和持久化调用链，但文件路径以当前版本为准。

- 把总耗时拆成：任务发现与入队、队列等待、ExifTool 实际读取、结果转换、数据库写入、必要的下游任务。
- 分别测量 JPG、NEF 与视频等代表性样本；区分冷缓存与热缓存、低并发与高并发，记录磁盘繁忙度。
- 先验证 ExifTool 的进程池复用及并发设置，再讨论进程模型是否真的需要改变。
- 优化前后使用相同样本、硬件、数据集状态和并发条件，报告每秒处理量、P50/P95、CPU、RSS、磁盘 I/O 和失败率。
- 不使用真实私人照片作为公开测试用例，不把路径、EXIF 中的隐私字段或照片内容写入提交与 CI 日志。

## 队列专项

在更改 BullMQ / Valkey / job 生产者前，画出实际的状态及事件流，确认：

- 去重键的粒度、有效生命周期以及重复扫描是否再次入队；
- job 在 waiting、active、completed、failed、retry 等状态之间的转移；
- 重试、超时、重启、幂等和失败恢复是否会导致重复执行或永久积压；
- 并发控制、资源争用与取消操作的可观测性。

优先修复调度逻辑与资源限制；不得仅为性能指标直接替换队列基础设施，也不得靠清理生产任务掩盖问题。

## API / Web 展示专项

- 先确认官方 Web 或既有 API 能否展示需要的信息；能复用就不新增端点。
- 必须新增时使用独立的管理接口和清晰的权限约束；避免改写已有 DTO、错误码、路由或照片元数据字段的含义。
- Web 管理 UI 只在存在明确展示需求时修改，不能因此要求官方移动端升级或自定义客户端。
- 完成后检查既有 Web 与官方移动端关键流程所依赖的 API 是否保持兼容；新增接口也应覆盖鉴权与错误路径测试。

## 开发/发布分工

- **NAS/Homelab**：隔离开发实例、热重载或增量构建、定向测试、基准测试与快速验证。
- **GitHub**：Pull Request 评审与主分支完整检查；合入稳定 `main` 后构建带版本标识的发布镜像。
- CI/CD 尚未实现时只记录目标分工，不得把计划描述成已部署功能；不得在首次搭建时自动替换生产镜像。

## 完成交付格式

简短说明：**改了什么、API/客户端影响、实际验证结果、性能对照（适用时）、回退和上游同步风险**。缺失的数据明确标注未测量，不推断结论。
