# iPhone 外部库备份

此功能保持官方客户端和既有上传、同步 API 的结构不变，默认关闭。只为管理员指定的一个 External Library 启用，由该库的所有者接收新上传。共享链接上传以及其他用户沿用原行为。

## 文件和备份语义

- 新原片实际归属于指定 External Library，保留文件内容，按拍摄当地时间保存到 `MobileBackup/iPhone/YYYY/MM/IMG_yyyyMMdd_HHmmss.原扩展名`。
- 例如拍摄时间为 `2026-11-03 11:10:00 +08:00`、扩展名为 `.HEIC`，则保存为 `MobileBackup/iPhone/2026/11/IMG_20261103_111000.HEIC`。
- 优先采用 Immich 现有 EXIF 拍摄时间选择顺序；缺少 EXIF 时使用客户端提供的文件创建时间，按配置时区归档，不采用请求到达时间。
- 同秒不同内容的文件追加 `+1`、`+2` 等后缀，已有文件绝不覆盖。Live Photo 的静态图和视频保留原有 API 关联。
- 该用户的普通上传接口共用此目的地，包括 Web 上传。官方接口没有可靠的仅限某一台 iPhone 的目标库选择参数。
- NAS 端删除只操作服务器资产和文件，不增加删除 iPhone 本地原片的行为。官方客户端收到永久删除通知后可能再次上传本地文件，这是明确接受的限制。

## 启用配置

在 API 和所有后台任务进程中配置相同的环境变量：

| 环境变量                                     | 含义                                                                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `IMMICH_FORK_IPHONE_BACKUP_LIBRARY_ID`       | 现有外部库的 UUID；未设置时不启用                                                                                        |
| `IMMICH_FORK_IPHONE_BACKUP_ROOT`             | 容器内完整备份根目录，例如 `/mnt/photos/MobileBackup/iPhone`                                                             |
| `IMMICH_FORK_IPHONE_BACKUP_TIME_ZONE`        | 无 EXIF 时区时的创建时间回退时区，默认 `Asia/Shanghai`                                                                   |
| `IMMICH_FORK_IPHONE_BACKUP_AUDIT`            | 设为 `true` 开启回归验收事件，默认关闭，需允许普通 Log 级别                                                              |
| `IMMICH_FORK_IPHONE_BACKUP_MIN_MONTH`        | 可选 YYYYMM 写入下界；本次部署为 `202611`。历史照片仍可按内容匹配                                                        |
| `IMMICH_FORK_IPHONE_BACKUP_HISTORICAL_ROOT`  | 可选历史上传暂存根目录；配置后，早于 `MIN_MONTH` 的未匹配文件写到这里并建立真实外部资产。默认未配置，仍返回原有月份错误  |
| `IMMICH_FORK_IPHONE_BACKUP_UPLOADS_ENABLED`  | 设为 `false` 时在解析原片前暂停目标用户上传，浏览和同步继续可用                                                          |
| `IMMICH_FORK_IPHONE_BACKUP_VIDEOS_ENABLED`   | 设为 `false` 时目标用户只接收新照片，视频在 multipart 文件头校验时返回可重试的 503；默认允许视频                         |
| `IMMICH_FORK_IPHONE_BACKUP_FINGERPRINT_SCAN` | 设为 `false` 时普通库扫描不自动补算指纹，允许先抽样验证                                                                  |
| `IMMICH_FORK_IPHONE_BACKUP_CONCURRENCY`      | 补算任务同时读取的文件数，默认 `1`，只允许 `1` 或 `2`；本 NAS 当前使用按目录路径排序的单文件读取，避免交替读两个远隔文件 |

管理员需预先建立可读写的备份根目录，并将 NAS 上的 `~/Photos` 挂载到示例中的 `/mnt/photos`。这里的 `~` 指 NAS 用户家目录，容器不会展开 NAS 用户的 `~`。根目录必须属于指定库现有导入路径；排除规则不得覆盖新文件目的地。程序只允许在经过验证的目录内发布文件。

照片模式沿用上游文件名扩展名分类，在创建暂存文件前拒绝新视频；应用不会完整读取视频原片，但不能据此保证手机或代理未发送、缓冲请求体。已有视频仍可浏览、同步及通过请求头内容指纹复用。Live Photo 的动态部分也属于视频；当前官方客户端在其上传失败后仍尝试上传静态图。手机可能继续尝试被拒绝的视频并显示失败，服务端不会将拒绝伪装成已备份。恢复时将视频开关改为 `true` 或移除，并重建服务容器；不需要数据库迁移或重置手机索引。

历史上传暂存用于收集手机尚未匹配的原片。管理员需预先创建并单独挂载可写目录，例如 `/mnt/photos/UploadReview`；它必须位于目标库现有导入范围内，与常规归档根目录互不包含，且不能被库排除规则覆盖。服务端解析符号链接后重新验证上述边界，年月子目录也沿用逐层越界检查。该选项不放开常规归档目录的历史月份写入：11 月门槛前的文件按拍摄时间保存到暂存根目录的 `YYYY/MM`，11 月及之后仍写入常规根目录。已知内容仍先判重，同秒不同内容追加 `+1` 等后缀，原片不改写、不覆盖；原始文件名保留在资产记录中。

暂存成功返回既有的真实资产创建响应，手机会将这些原片记为已备份；后续重试与同步沿用真实内容 SHA-1、资产 ID 和原有权限。缩略图、元数据与同步会产生正常后台负载，不能把此模式当作不建档的临时抓包。开启验收日志后，这些 `external_asset_created` 事件附带 `historical: true`，不记录原片名、路径或内容哈希。暂存失败沿用原有文件与记录回滚。移除该环境变量并重建容器可恢复后续历史写入门禁，已暂存的文件和资产继续保留、判重及同步；分析完成后应另行安排归档，不能直接删除仍承担备份职责的暂存原片。启用与关闭均无需数据库迁移，不修改移动端或官方 API/SDK。

启用需要先备份数据库，评审并应用新增迁移。内容指纹迁移新增可空字段和索引；客户端唯一性修复另增加持久匹配映射、初始化已有资产映射，并标记受影响用户的会话重建远端索引。迁移均不修改既有原片。真实图库的迁移、补算和部署应单独授权，不随代码测试自动执行。

## 元数据版本共用原片与暂存清理

默认使用显式管理流程；仅设置 `IMMICH_FORK_IPHONE_BACKUP_AUTO_REFERENCES=true` 时启用下述自动协调器。当前接受不超过 64 MiB 的 JPEG/PNG 及严格支持的静态 HEIC 原片；视频本体、带 sidecar 的资产、未知 HEIF 结构以及无法唯一安全处理的堆叠继续保留原文件。先查询已持久化的图像本体索引，再检查记录时间附近及已有 CLIP 索引的有限候选；不要求文件名或时间相同，不新建视觉向量或重建索引。相似度只缩小范围，必须继续验证 ExifTool 图像 SHA-256、逐字节相同的图像编码以及显示配置。JPEG 保留 ICC/Adobe 配置校验，PNG 仅将 EXIF/文本块作为独立元数据，其余色彩、动画和未知块均须完全相同。HEIC 还必须严格验证全部编码项、辅助图、解码配置和引用关系。评分、标签、GPS、描述等元数据可不同；每个逻辑版本保留自己的完整元数据和恢复配方，不覆盖字段。只有恢复结果完整 SHA-1 等于手机原文件时，才允许共用编码数据。

Live Photo 仅共用静态照片部分，两个逻辑照片分别保留原有 `livePhotoVideoId`，不移动、覆盖、替换或删除关联视频；下载仍按原有照片与视频关联选择成员。静态照片的元数据恢复包含原有标识字段，完整字节必须复原。这里不承诺两个版本的视频相同，也不对视频本体做自动清理。

每个手机版本保留自己的资产 ID 和 `backupChecksum`，同步仍下发该版本的整文件 SHA-1；`contentChecksum` 则保存实际共用 NAS 原片的内容 SHA-1。`backupSourceId` 指向同用户同库的独立物理资产，禁止跨用户、引用自身和引用链。已有客户端代表和其他资产的匹配哈希不重置。已有 NEF 等堆叠保留原 ID、主图和成员，不能安全并入的情况报告为冲突。

`backupMetadata` 保存 gzip 压缩的无损 JPEG/PNG 恢复配方，只保留版本自己的元数据字节；编码图像始终取自 NAS 原片。下载原片和 ZIP 打包时使用请求专属临时文件重建手机版本，并校验完整 SHA-1；原片下载继续使用原有文件发送及 Range 处理，传输结束回收临时文件。数据库备份必须包含这些恢复配方；它们不是可随意清掉的缓存。NAS 图像数据实际改变时拒绝恢复，不返回错误内容。当前未实现源原片内容变化后的自动等价重新确认，扫描撤销关联后需显式复核。回退到不支持 PNG 的旧镜像前，须先用当前版本的 `restore` 恢复 PNG 完整文件并撤销相应引用。

管理工具编译后位于 `server/dist/bin/reconcile-iphone-backup.js`，使用当前服务的环境配置和数据库，不启动 API 或执行迁移：

```sh
# 只读检查一批；报告含私人路径和指纹，必须保存在私有持久目录。
node dist/bin/reconcile-iphone-backup.js assess /data/backups/reference-report.json 100
# 应用已核对的具体计划，只改关联和堆叠，不删除暂存文件。
node dist/bin/reconcile-iphone-backup.js prepare --apply /data/backups/reference-report.json
# 同一手机会话确认新的 AssetV2 和 SyncCompleteV1 后，才允许清理报告内的匹配文件。
node dist/bin/reconcile-iphone-backup.js cleanup --apply /data/backups/reference-report.json PHONE_SESSION_UUID
# 回退时先恢复完整暂存原片，再撤销引用，不能先回退 schema 或服务镜像。
node dist/bin/reconcile-iphone-backup.js restore --apply /data/backups/reference-report.json
```

报告中的未匹配、不支持、冲突和读取异常都保留文件。`assess` 可用第四个参数接续上一批最后资产 ID；每批最多 2000 项，文件顺序读取，不进行全库原片重哈希。`prepare` 与 `cleanup` 使用上传/导入共用的数据库锁，重新读取资产、实际文件和元数据，不把旧报告当作可信证明。清理还要求：会话属于目标用户、无待处理索引重置、资产同步游标已越过版本变更、同步结束确认已更新、恢复配方能逐字节复原手机版本，以及没有其他资产仍使用待清理路径。只移除指定暂存根内的完整副本，不清空整个目录。

删除版本资产时不删除共用原片；物理原片离线、删除、改变内容或转移归属时撤销版本匹配，防止继续显示虚假的备份关系。普通库扫描不把版本当作另一份物理原片，也不会重新导入已关联但尚未清理的暂存文件。迁移 `1793898000000-ForkIphoneBackupReferences` 不重置现有会话、不修改原片；存在版本引用时拒绝回退，必须先运行 `restore`。生产迁移前备份数据库，清理前保留私有报告与实际手机同步验收结果。

### 上传后的自动关联与确认清理

自动协调器复用上述校验、关联和恢复逻辑，不改变上传 HTTP 响应，也不等待去重才完成备份。必须先完成元数据提取并从手机版完整文件生成原始预览及 ThumbHash，避免切换共享原片影响方向和显示；缩略图成功事件可开始检查，不要求启用 ML。已有视觉索引生成成功后可再补查一次。重启及事件入队失败由 30 秒巡检补齐，每次最多安排 100 个匹配和 100 个已确认清理任务，只扫描配置库的历史暂存范围，不重置已匹配资产，不扫描所有 NAS 原片。无法匹配、重新编码、不同版本及未支持格式仍保留实际上传文件，其完整哈希继续正常参与官方客户端备份匹配。匹配成功也不表示首轮文件没有经过网络传输。

独立 BullMQ 队列 `fork-iphone-references` 跨进程全局并发为 1。任务键包含操作、资产 ID、资产 `updateId`，匹配另区分有无已有视觉向量；重复事件或重启不重新读取同一版本。排队后资产变化会跳过过期任务，巡检为新版本补齐。完成及失败任务保留在 Redis；单次失败不无限重试、不影响官方上传，后续分页不会被失败页阻塞。服务停止时等待当前有限检查结束，未开始任务保持持久化。当前原片或候选有变化时仍需显式复查；不能把一个历史未匹配结果解释为图库永远没有该照片。队列控制数据沿用既有 Redis 持久化备份，不能当作可随意清空的缓存。

自动清理还必须显式配置 `IMMICH_FORK_IPHONE_BACKUP_REFERENCE_SESSION_ID` 为目标用户的手机会话 UUID。未配置时只关联并保留完整副本。协调器同时检查该会话归属、无待处理同步重置、AssetV2 游标及 AssetV2/SyncCompleteV1 的真实确认时间；执行时再次验证完整恢复和文件占用。不会伪造确认、使用其他用户会话或自动恢复回收站照片。会话被删除或更换后需更新配置，不能因此放松清理保护。

```sh
# 只查看独立队列的计数、暂停状态和最多 20 个失败任务 ID。
node dist/bin/iphone-backup-reference-queue.js status
# 显式暂停或恢复，不影响官方上传队列和已有手机匹配。
node dist/bin/iphone-backup-reference-queue.js pause --apply
node dist/bin/iphone-backup-reference-queue.js resume --apply
# 单个失败任务只在管理员明确要求后重试。
node dist/bin/iphone-backup-reference-queue.js retry --apply JOB_ID
```

自动关联沿用原有 HTTP 端点和 SDK 字段。关闭自动化环境开关并重启可停止新协调；已有引用和恢复资料必须保留，不能回退到不支持恢复配方的镜像。暂停队列不会自动恢复，已完成记录也不会在启动时删除。

### 图像本体索引和后续元数据修订

迁移 `1793952000000` 保存严格图像指纹、可信上传来源和不可变源底稿；`1793952000001` 更新引用维护函数，不重置已有手机同步。图像指纹用于查候选，拍摄时间、GPS、关键字和文件名不再限制已索引候选。最终建立关联仍要求实际编码数据一致，并逐字节恢复手机原文件、验证完整 SHA-1；视觉相似度不能授权关联或删除。

自动协调现在同时覆盖历史暂存文件及普通备份目录内的可信新上传。可信来源只由上传发布后的内部事件写入，早于异步元数据任务；公开元数据不能赋予 NAS 原片可清理身份。新上传先保存自己的原始资料和底稿。NAS 软件以后改写时间、GPS、标签时，有界巡检会重新验证来源，必要时恢复一个完整手机版本到历史暂存目录，经过它自己的元数据和预览任务后再关联；不需要手机重新传输已经保存的原版本。已恢复版本的删除标记保留，后台不会反复复活用户删除的版本。

必须将 `IMMICH_FORK_IPHONE_BACKUP_SNAPSHOT_ROOT` 指向已有、权限 `0700`、位于所有外部库导入目录之外的独立持久目录。底稿使用独立 inode 的 COW 克隆，文件系统不支持时退回完整复制；不能把 NAS 原文件硬链接当作不可变底稿。每份底稿均验证完整 SHA-1。下载、ZIP、元数据及预览任务使用固定底稿恢复手机版本，NAS 真正改变图像数据后也不能用新图像替代旧备份。底稿目录必须与数据库及恢复配方一起保留；它的逻辑大小不等于 Btrfs 实际新增占用，后续元数据软件重写仍可能分配新的数据块，不能承诺零额外空间。

本体索引和源复核使用既有独立队列，全局并发为一；匹配、手机确认后的清理优先于后台索引。生产者有全局入队保护及待处理上限，定期只安排有限页。索引成功推进持久代数，使先前未命中的已完成检查有机会重查；失败任务仍需显式重试。仅对已有引用或可信来源做文件签名巡检，普通旧 NAS 文件在建立索引时只读，不全部创建底稿。管理员暂停状态、已完成和失败记录在重启后保留。

当前严格去重支持上限 64 MiB 的实际 JPEG/PNG 和有限静态 HEIC。JPEG 色彩配置与编码结构、PNG 非文本块仍参与严格校验，不能只凭解码后的画面相似共用。静态 HEIC 除图像数据摘要外，还解析所有 item/extent，保护 hvcC、iprp、辅助图和引用关系，不采用仅主图哈希。仅 Exif 和未编码的 RDF/XML 项视为独立元数据；未知盒、属性、编码、轨道、外部引用或重叠范围均保留完整上传。JPEG/PNG 沿用 v1 恢复配方，HEIC 使用显式 v2 配方，同时验证结构指纹和最终整文件 SHA-1。不能直接回退到只支持 v1 的镜像，必须保留可读 v2 的版本，或先恢复所有独立完整文件。

元数据恢复资料超限的已支持图片保留完整备份及初始快照，不因去重限制让上传失败。未知 HEIF/AVIF/动画、视频、超限文件及其他未证明可恢复的格式继续保留完整备份，不自动清理。旧能力下已完成的“不支持”任务在能力升级后只补查一次；失败任务继续等待明确重试。官方手机仍使用完整文件哈希；对从未保存过的手机元数据版本，服务器不能从 NAS 的另一个完整哈希推算出未知手机哈希，首次可能仍需接收文件。

已捕获的普通上传也按当前完整摘要优先读取不可变快照，防止 NAS 改写至下一轮巡检之间，下载返回与已下发哈希不同的原片。iOS 单个 RAW＋JPEG 项目仍由官方客户端选择一个当前图像资源上传；服务端自动 RAW 配对只处理已实际收到的文件。Live Photo 的运动文件是独立资产，静态版本共享不删除其 MOV；单凭手机剩余计数为零不能证明全部资源已到齐。

## 首次备份准备

1. 对目标外部库执行正常扫描，完成既有文件的内容指纹补算。补算流式读取原片，增加磁盘读取量；未提供真实图库性能基准。
2. 确认扫描任务全部成功，再让手机完成远端资产索引同步，并完成所选备份相册的本地哈希准备。
3. 手机根据相同内容 SHA-1 关联已有资产，跳过已经在目标库中的文件；只传输未匹配的文件。
4. 上传时服务端仍进行内容检查，以处理客户端状态尚未同步、并发请求和重试。此兜底不能保证文件从未经过网络传输。

外部库原有 `checksum` 继续表示路径，`contentChecksum` 保存每份文件的真实内容指纹。同内容不同路径的文件保留各自资产 ID，不合并或删除。官方手机数据库要求同用户、同外部库的下发 checksum 唯一，因此另用内部字段 `clientChecksum` 为每组内容副本持久选择一个在线、未删除的代表；该代表下发内容指纹，其他副本仍下发路径标识。手机只将代表与本地原片关联，其他副本仍可作为独立远端资产查看。所有副本的原始内容指纹仍参与服务端上传判重，预检及头部判重优先复用代表。

数据库触发器覆盖上传、扫描与独立补算，库级事务锁和唯一索引防止并发分配同一指纹。后到的副本即使 ID 或创建时间更小，也不会取代已有代表。代表离线、进入回收站、永久删除或改变内容后，仍可用的副本接手匹配；旧代表撤销先于新代表晋升。UUID v7 的随机尾部不保证同毫秒内排序，更新交接仅等待越过旧记录所在毫秒后再生成新代表的 updateId，保持增量流顺序。原片仍只读，其他官方队列不受该锁约束。

迁移 `1793718000000-ForkIphoneClientChecksum` 为已有内容选择代表，并用官方 `isPendingSyncReset` / `SyncResetV1` 流程通知受影响用户重建手机远端索引，避免已缓存的旧指纹冲突。手机照片文件和本地哈希不会因此删除；官方重置流程会清除远端索引并解除本地相册的远端关联，恢复同步后需要检查相册关联设置。仅重试旧版同步或清理服务端日志不能修复手机已保存的冲突映射。其他用户不设置重置标记。

此修复不改变 HTTP 路径、状态码、DTO 或鉴权，不增加官方 SDK 字段，不修改移动端源码。列表、详情、推送以及本人、相簿和伙伴同步统一使用 `clientChecksum`，不直接将所有副本的原始内容指纹作为下发 checksum。迁移回退保留原始路径和内容指纹，但旧镜像会重新下发冲突指纹，不能把切回旧镜像当作手机同步恢复方案。生产迁移前需要一致数据库备份及恢复验证；真实迁移锁持有时间与全库吞吐尚未测量。

本次修复实际通过 265 项定向单测及 78 项不重复的隔离集成场景，包括 PostgreSQL 响应进入手机相同唯一索引和 upsert 语义的内存 SQLite、持久代表不被后到副本抢占、代表离线/回收站/删除/内容变化后的增量交接、并发补算、用户及库隔离、旧数据迁移与官方远端重置、sql-tools 结构一致性、相簿及伙伴同步，以及既有 25 项准备进度场景。类型、ESLint、格式和 110 项迁移历史/顺序校验通过。尚未在实际 iPhone 上验收此修复。

大图库应先暂停上传和自动指纹补算，再通过 `server/dist/bin/iphone-backup-fingerprints.js` 执行 `status`、`sample 24` 和 `verify 24`。抽样只选择不超过 128 MiB 的文件，按格式轮转；`backfill 1000` 每次最多补算指定数量的缺失指纹。命令只读原片，只更新已有资产的内容指纹，不新增照片、不改文件名、不启动元数据任务。抽样输出 CPU、RSS、I/O 和耗时分布，缓存状态明确记为未控制。旧文件匹配准备完成之前，不应对手机约 8 万张“最近项目”开放全量上传。

当备份目录已有历史照片时，可将整个目录挂载为可写，再对所有历史年份及当前年起始月之前的目录叠加只读挂载；其他图库根目录保持只读。这样未来月份可以创建，既有历史原片仍由挂载权限保护。写入月份还受服务端下界校验，不能仅依赖 UI 选择。

## 管理页中的匹配准备进度

管理员打开“任务队列 → 有向图”，可在图库导入节点上方看到“历史照片匹配”虚线分支。该分支需显式启动，不是元数据或缩略图的前置条件，也不改变原有队列的暂停状态。节点每 6 秒刷新数据库中的就绪量与剩余量；手动模式空闲且仍有缺失指纹时显示“等待下一批”，持续模式的批次间隔显示“排队中”，均不显示完成。单照片追踪视图不混用全库匹配状态。

点击节点可以选择“开始持续准备”或仅“处理下一批”，也可暂停和重试失败批次。每批默认及最多 5,000 张，普通批次最多读取 8 GiB；持续模式在完成事件到达后立即协调下一批，没有强制批间冷却，直到全库就绪、暂停或失败。每 5 秒的后台巡检仅用于完成事件丢失或重启后的恢复。手动模式每批结束后停止。优先图片，再处理视频，每类内部按完整原路径和资产 ID 稳定排序，尽量连续处理同目录文件。路径顺序不等同于物理数据块顺序，不移动、整理或改写原片。单个文件超过 8 GiB 时独占一个批次，沿用流式哈希，不与其他文件同时读取；若本批已处理或预留其他文件，则先结束本批，下一批再处理该超大文件，不跳过资产。暂停在当前在途文件处理完后生效，因此超大文件可能延长暂停等待；批次中仍逐项保存和更新进度，不必等 5,000 张全部完成。刷新失败会保留旧数据并标记过期，禁止提交控制命令。

独立 BullMQ 队列名为 `fork-iphone-fingerprints`，沿用现有 Redis 连接与前缀；不新增官方队列或任务枚举。每库一个固定 jobId，队列任务全局并发为 1；任务内可同时处理最多两个文件。每波次开始前预留所有在途文件的总字节预算，普通批次受每批 8 GiB 限制，只有独占批次的单个超大文件允许超过预算。暂停后等待当前在途文件结束，不再接收下一波次。一项失败会保留另一在途文件的成功结果，记录准确完成数、字节和失败资产 ID，再停止批次；显式重试只选尚缺指纹的资产。批次只尝试一次，失败保留且要求显式重试。进程意外退出使用 BullMQ 的有限 stalled 恢复，完成项已存入数据库，重入时只选缺失指纹。管理员暂停状态在重启后保留；正常结束和失败均保留本批计数、字节及安全错误码，不记录私人路径。批次完成日志增加 elapsedMs 和 concurrency，供实际运行验证速度。文件读取前后校验大小、mtime 和 inode，数据库按原路径与 updateId 条件更新，拒绝删除、扫描和其他任务产生的过期快照。

旧版因 `FILE_TOO_LARGE` 停止的批次在部署此修复后仍保留失败状态，需在管理页显式点击“重试”；已完成指纹不会重算，原有持续模式成功后继续接续。超大文件修复后，本套隔离 PostgreSQL、Valkey 集成测试共 25 项通过：新增或替换的 5 项场景覆盖单/双文件并发下的独占读取、已有普通文件时延后超大文件、读取失败停止与显式重试后自动接续。测试只模拟调度层看到的超大文件字节数，实际哈希和数据库写入使用小型合成文件；未执行真实大于 8 GiB 文件的吞吐或内存基准。回退旧版不需数据库迁移，但尚缺指纹的超大文件会再次触发旧版限制。

持续模式与批次上限按库保存在 Redis；API 或后台进程重启后仍能接续，管理员暂停状态不会被自动恢复。全库就绪后关闭接续，不自动追踪以后新增的文件，也不自动开启手机上传。协调器与管理员命令共用独立 PostgreSQL advisory lock，串行替换已完成任务，防止多个实例误删另一实例刚创建的新批次。后台定时检查与完成事件解耦，失败任务始终保留；重试仍需明确管理员操作。Redis 控制数据使用现有队列存储的持久化与备份策略，不新增存储服务。

管理接口为 `GET/PUT /api/admin/fork/iphone-backup`，分别要求管理员及 `queue.read` / `queue.update` 权限。PUT 接收 `command: start|continue|pause|resume|retry` 和可选 `limit: 1..5000`，默认 5,000；continue 显式开启持续模式，start 停止后续自动接续并提交单批，resume 保留原有模式。已排队或执行中的同 ID 批次不会被重复启动或重置。响应的 continuous 表示仍有待处理照片的持续模式。请求不能指定库或路径，也不能开启手机上传。此 Fork 专用控制器显式排除在官方 OpenAPI 生成链路之外，由 Web 管理页的独立客户端调用；不修改官方 SDK 或移动端。原有官方 HTTP 接口和响应结构不变，无新增数据库迁移。回退到最多只支持 1,000 张的旧版前，需先用新版将持续批次改回 1,000 并暂停，确认在途任务结束后再切镜像；旧版不能读取 Redis 中的 5,000 上限。既有指纹保留。

当前在独立 PostgreSQL、Valkey 与合成文件上验证 21 项集成场景，覆盖统计不启动任务、并发去重、有界批次、暂停与重启恢复、失败不自动重试、读预算、拒绝过期指纹、多实例协调及目录顺序。批次升级另验证了 5,000 上限的请求和消费链路：单批实际处理 1,002 个文件，以及两批在 5 秒巡检前完成的即时接续。页面实际 iPhone 本地匹配结果仍需在手机上验收。

大批次仅减少调度切换和固定休息，不会合并成一次磁盘读取。按每 1,000 张执行约 90～160 秒估算，取消几秒休息的收益通常只是几个百分点；文件打开、元数据和 SSD 缓存等待仍影响小文件吞吐。完成事件与巡检请求合并并保留待处理信号，协调器和管理命令继续通过同一数据库锁串行化；失败和暂停不触发自动恢复。

### 2026-11-03 读取速度诊断

基线代码为 b556393f338e，NAS 为 i7-1165G7、约 23 GiB 内存，原片位于单盘 HDD 加 119 GiB SATA SSD 缓存的卷，PostgreSQL 位于 NVMe 卷。当时完整批次每 1,000 张约 6～7 分钟，约 6 GiB 原片；5 秒批间冷却占比较小。暂停匹配任务后，24 张真实图片的阶段测量共读取 180,161,749 字节：总耗时 4.031 秒，其中原片内容指纹 3.778 秒、数据库更新 0.140 秒；进程 CPU 0.910 秒，峰值 RSS 237,612 KiB，实际设备读取 339,525,632 字节，缓存状态未控制。

随后对固定的 24 个样本、457,429,200 字节执行只读微基准，覆盖 JPG、JPEG、HEIC、PNG、DNG、NEF、MOV、MP4、INSP、INSV、GIF、TIF，各 2 个文件。先完整预读一次；每轮仅用 vmtouch 驱逐这些样本的 OS 页缓存，不清空全机缓存。NAS SSD 缓存未清空，其内部命中率未控制；采用 ABBA 顺序交替对照，所有轮次逐文件校验相同 SHA-1。样本清单、原始计数与 I/O 记录保存在 NAS 私有部署目录，不提交照片路径或内容。

64 KiB 与 1 MiB 缓冲区的 ABBA 对照未显示更大缓冲区有收益，因此保留既有 64 KiB 实现。保持相同缓冲区后，对单文件读取和两文件并行执行另一组 ABBA：单文件两轮耗时 4.431 / 4.187 秒，两文件并行 2.449 / 1.616 秒，合并样本读取吞吐约提升 2.12 倍。单文件 P50 为 80.5～97.0 毫秒、P95 为 608～686 毫秒；两文件 P50 为 99.7～118.0 毫秒、P95 为 324～653 毫秒。每轮 CPU 分别为 1.301～1.404 秒与 1.098～1.194 秒；峰值 RSS 为 231,896～238,180 KiB 与 235,424～239,868 KiB；实际设备读取约 557.7～558.0 MB，逻辑读取约 457.5 MB。该结果只代表这组缓存条件下的原片读取阶段，不代表全库或含数据库写入的固定提速承诺。

本次仅为补算增加可回退的 1/2 文件并发配置，不调整其他队列或 NAS SSD 缓存策略。双文件模式新增 5 项隔离集成测试，验证真实并行与内容正确性、合计字节预算、暂停只结束在途文件、一失败一成功的准确计数及显式重试、单文件批次上限，共 19 项集成测试通过。回退时先暂停匹配，将并发配置改为 1 并重启，再恢复持续准备；无需回滚数据库或改动原片。

### 持续运行与访问顺序补充

双文件模式曾在一批 1,000 张、6,686,777,312 字节上记录 130.553 秒，但随后三个完整批次回到 349.292～370.924 秒，不能把短时微基准或首批结果当作持续吞吐。再次观测时，缓存 SSD 利用率约 93%、写等待约 283 毫秒，HDD 利用率约 9%；SSD 缓存填充等待也是实际瓶颈。缓存原设置为每段连续访问超过 1 MiB 才跳过后续顺序读取，相关设置保持原值。

对 256 个尚未匹配、未预热的手机目录文件分成互不重复的 ABBA 队列，实际计算并保存内容指纹。双文件 UUID 顺序两组为 55.8 / 43.7 MiB/s，单文件路径顺序为 64.7 / 34.8 MiB/s；各组格式与文件大小分布不同，缓存命中率未控制，因此该首次读取试验不能证明固定提速比例。

额外使用只读 FIEMAP 区段查询检查同一组 256 个文件，均为单区段文件：UUID 顺序相邻文件首尾跳转距离中位数约 415.7 GiB，路径顺序约 2.01 GiB，按首区段地址排序约 21.6 MiB。路径排序能减少大范围跳转，但只有 5/255 对在前向 128 KiB 内，不能称为真正物理顺序；Btrfs 文件系统报告的区段地址也不能无条件等同于实际设备布局。区段查询仅用于诊断，没有修改布局、关闭 SSD 缓存或在服务中引入物理地址索引。

当前最小变更将随机 UUID 取批改为类型、路径、ID 顺序，并使用一个文件读取流；已补算记录保留，不重置或遗漏未完成项。新增隔离回归验证 UUID 顺序与目录顺序相反时仍先完成同目录文件，连同既有并发、预算、暂停、重入等共 20 项集成测试通过。实际持续性能仍需结合后续完整批次日志判断，不能仅以图中每秒完成张数比较大小不同的文件。

## 本地优先查看与离线验证

官方客户端已经按 checksum 关联远端和本地资产。新内容指纹通过原有同步接口下发，列表和资产详情使用一致的匹配值，手机不需要安装定制版。

在手机设置的高级选项中关闭“优先使用远程图片”。待本地与远端索引准备完成后，选择一张本机确实保存完整原片、未经过 Immich 编辑的匹配照片，断开 NAS 网络并打开大图，应能走本地图片加载器，而非仅显示远端缩略图或 ThumbHash 占位图。只在 iCloud 中、尚未下载到手机的原片不满足此验证起始条件。

这项体验仍需在实际官方 iPhone 客户端上验收；服务端集成测试只能验证下发的内容指纹和关联数据，不能替代 iOS PhotoKit 行为验证。

## 回归验收日志

验收前在 API 和后台进程启用 `IMMICH_FORK_IPHONE_BACKUP_AUDIT=true`，通过 `IphoneBackupAudit` 前缀查找结构化事件。记录测试起止时间；按 `uploadId` 串联同次接收，按 `assetId` 串联已有云端资产。新增事件只记录不透明 ID、字节数和结果，不记录原片名、目录、完整内容哈希或 EXIF。

| 事件                                             | 能证明什么                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------- |
| `fingerprint_ready`                              | 对应外部资产的内容指纹已经写入数据库                                       |
| `sync_asset_sent`                                | 对应资产已写入同步响应流；不代表手机已接收并完成本地关联                   |
| `upload_stream_started` / `upload_stream_failed` | 原片流已进入应用，或流失败时应用已读到的原片字节数                         |
| `upload_received`                                | 原片已完整接收，包含实际原片和 XMP 字节数                                  |
| `duplicate_after_receive`                        | 原片完整上传后判重，复用已有资产并清理本次暂存副本；这不算“没有上传”       |
| `header_duplicate`                               | 上传请求头命中已有资产，应用未解析原片；不能据此断言代理或网络未接收请求体 |
| `upload_precheck`                                | 指纹预检的检查数和重复数；不代表客户端最终执行了跳过                       |
| `external_asset_created`                         | 新建了外部库资产，原子发布路径未覆盖已有文件，记录 `overwrite=false`       |
| `filename_collision` / `upload_rolled_back`      | 重名后尝试追加序号，或失败后清理本次已发布副本                             |

手机在本地比较后直接跳过的照片没有上传请求，服务端不能为此虚构逐照片的 `client_skipped` 事件。验证需要组合证据：选一张云端与手机内容一致的照片和一张仅在手机的新照片；确认指纹就绪、手机远端同步与本地哈希完成；在固定测试窗口观察手机备份统计、新照片成功上传的日志、已有照片是否出现“上传后判重”，以及对应云端资产数、原片大小和 SHA-256 前后是否变化。若需要直接证明客户端针对某张照片作出的跳过决定，还需要手机本地索引或客户端日志；单靠服务端“没有日志”不够。

所有字节字段都是应用解析的文件数据，不是设备总网络流量或反向代理接收量。iCloud 下载、缩略图请求和同步索引流量应与向 NAS 上传原片的流量分开。

## 验收与回退

验收应覆盖首次备份、重复与并发上传、同秒重名、库扫描后无第二条资产、用户隔离、无 EXIF 时间回退、离线文件撤销匹配以及 NAS 永久删除后允许重新上传的已接受限制。记录实际新增文件数和客户端上传流量，不能仅依据数据库没有重复行判断没有重复传输。

本次本地检查（包含验收日志补充）：349 项定向单测、40 项数据库与文件系统集成测试通过；TypeScript 检查、ESLint、Prettier、Nest 构建及 108 项迁移顺序与历史保留检查通过。额外运行的既有外部库集成套件有 3 项因缺少 `glarus.nef` 样本失败，不能记为全套通过。EXIF 时间在新增集成测试中使用可控标签，真实 iPhone、HEIC/视频元数据、离线 PhotoKit 显示及生产图库吞吐量仍未实测。

目标文件系统需要支持硬链接，以便完整复制后原子发布且不覆盖现有文件；不支持时上传失败，不降级为覆盖写入。Fork 既有的 INSV 和大于 3 GiB 视频扫描延后策略保持不变，这些尚未建档的既有文件不在首次指纹补算覆盖范围内。

移除目标库环境配置并重启服务可停止新上传路由，已有外部文件不移动、不转换归属。已保存的内容指纹继续用于已有资产的客户端匹配；回退到旧服务端版本时仍保留原有路径 checksum。数据库 down 迁移会删除新增指纹及索引，但不会移回或删除已归档文件；生产回退也需要单独评审。
