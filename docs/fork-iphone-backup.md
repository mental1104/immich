# iPhone 外部库备份

此功能保持官方客户端和既有上传、同步 API 的结构不变，默认关闭。只为管理员指定的一个 External Library 启用，由该库的所有者接收新上传。共享链接上传以及其他用户沿用原行为。

## 文件和备份语义

- 新原片实际归属于指定 External Library，保留文件内容，按拍摄当地时间保存到 `MobileBackup/iPhone/YYYY/MM/IMG_yyyyMMdd_HHmmss.原扩展名`。
- 例如拍摄时间为 `2026-11-03 11:10:00 +08:00`、扩展名为 `.HEIC`，则保存为 `MobileBackup/iPhone/2026/11/IMG_20261103_111000.HEIC`。
- 优先采用 Immich 现有 EXIF 拍摄时间选择顺序；缺少 EXIF 时使用客户端提供的文件创建时间，按配置时区归档，不采用请求到达时间。
- 同秒不同内容的文件追加 `+1`、`+2` 等后缀，已有文件绝不覆盖。Live Photo 的静态图和视频保留原有 API 关联。
- 该用户的普通上传接口共用此目的地，包括 Web 上传。官方接口没有可靠的仅限某一台 iPhone 的目标库选择参数。
- NAS 端删除只操作服务器资产和文件，不增加删除 iPhone 本地原片的行为。官方客户端收到永久删除通知后可能再次上传本地文件，这是明确接受的限制。

## 启用配置

在 API 和所有后台任务进程中配置相同的环境变量：

| 环境变量 | 含义 |
| --- | --- |
| `IMMICH_FORK_IPHONE_BACKUP_LIBRARY_ID` | 现有外部库的 UUID；未设置时不启用 |
| `IMMICH_FORK_IPHONE_BACKUP_ROOT` | 容器内完整备份根目录，例如 `/mnt/photos/MobileBackup/iPhone` |
| `IMMICH_FORK_IPHONE_BACKUP_TIME_ZONE` | 无 EXIF 时区时的创建时间回退时区，默认 `Asia/Shanghai` |
| `IMMICH_FORK_IPHONE_BACKUP_AUDIT` | 设为 `true` 开启回归验收事件，默认关闭，需允许普通 Log 级别 |
| `IMMICH_FORK_IPHONE_BACKUP_MIN_MONTH` | 可选 YYYYMM 写入下界；本次部署为 `202611`。历史照片仍可按内容匹配 |
| `IMMICH_FORK_IPHONE_BACKUP_UPLOADS_ENABLED` | 设为 `false` 时在解析原片前暂停目标用户上传，浏览和同步继续可用 |
| `IMMICH_FORK_IPHONE_BACKUP_FINGERPRINT_SCAN` | 设为 `false` 时普通库扫描不自动补算指纹，允许先抽样验证 |
| `IMMICH_FORK_IPHONE_BACKUP_CONCURRENCY` | 补算任务同时读取的文件数，默认 `1`，只允许 `1` 或 `2`；本 NAS 经对照测量使用 `2` |

管理员需预先建立可读写的备份根目录，并将 NAS 上的 `~/Photos` 挂载到示例中的 `/mnt/photos`。这里的 `~` 指 NAS 用户家目录，容器不会展开 NAS 用户的 `~`。根目录必须属于指定库现有导入路径；排除规则不得覆盖新文件目的地。程序只允许在经过验证的目录内发布文件。

启用需要先备份数据库，评审并应用新增迁移。迁移只新增可空内容指纹和索引，不修改任何既有原片。真实图库的迁移、补算和部署应单独授权，不随代码测试自动执行。

## 首次备份准备

1. 对目标外部库执行正常扫描，完成既有文件的内容指纹补算。补算流式读取原片，增加磁盘读取量；未提供真实图库性能基准。
2. 确认扫描任务全部成功，再让手机完成远端资产索引同步，并完成所选备份相册的本地哈希准备。
3. 手机根据相同内容 SHA-1 关联已有资产，跳过已经在目标库中的文件；只传输未匹配的文件。
4. 上传时服务端仍进行内容检查，以处理客户端状态尚未同步、并发请求和重试。此兜底不能保证文件从未经过网络传输。

外部库原有 `checksum` 继续表示路径，新增 `contentChecksum` 用于文件内容匹配。因此，同内容不同路径的既有文件仍保留各自资产 ID，不会被迁移合并。正常扫描会更新被修改文件的内容指纹，并撤销不可访问文件的匹配；文件监听也会更新既有路径的内容匹配。

大图库应先暂停上传和自动指纹补算，再通过 `server/dist/bin/iphone-backup-fingerprints.js` 执行 `status`、`sample 24` 和 `verify 24`。抽样只选择不超过 128 MiB 的文件，按格式轮转；`backfill 1000` 每次最多补算指定数量的缺失指纹。命令只读原片，只更新已有资产的内容指纹，不新增照片、不改文件名、不启动元数据任务。抽样输出 CPU、RSS、I/O 和耗时分布，缓存状态明确记为未控制。旧文件匹配准备完成之前，不应对手机约 8 万张“最近项目”开放全量上传。

当备份目录已有历史照片时，可将整个目录挂载为可写，再对所有历史年份及当前年起始月之前的目录叠加只读挂载；其他图库根目录保持只读。这样未来月份可以创建，既有历史原片仍由挂载权限保护。写入月份还受服务端下界校验，不能仅依赖 UI 选择。

## 管理页中的匹配准备进度

管理员打开“任务队列 → 有向图”，可在图库导入节点上方看到“历史照片匹配”虚线分支。该分支需显式启动，不是元数据或缩略图的前置条件，也不改变原有队列的暂停状态。节点每 6 秒刷新数据库中的就绪量与剩余量；手动模式空闲且仍有缺失指纹时显示“等待下一批”，持续模式的批次间隔显示“排队中”，均不显示完成。单照片追踪视图不混用全库匹配状态。

点击节点可以选择“开始持续准备”或仅“处理下一批”，也可暂停和重试失败批次。每批最多 1,000 张或读取 8 GiB；持续模式在批次完成后至少休息 5 秒，由后台每 5 秒检查并接续下一批，直到全库就绪、暂停或失败。手动模式每批结束后停止。优先图片，再处理视频。单个文件超过 8 GiB 会明确失败并保留资产 ID，不能静默跳过。暂停在当前文件处理完后生效，文件之间检查暂停状态。刷新失败会保留旧数据并标记过期，禁止提交控制命令。

独立 BullMQ 队列名为 `fork-iphone-fingerprints`，沿用现有 Redis 连接与前缀；不新增官方队列或任务枚举。每库一个固定 jobId，队列任务全局并发为 1；任务内可同时处理最多两个文件。每波次开始前预留所有在途文件的总字节预算，仍受每批 8 GiB 限制。暂停后等待当前在途文件结束，不再接收下一波次。一项失败会保留另一在途文件的成功结果，记录准确完成数、字节和失败资产 ID，再停止批次；显式重试只选尚缺指纹的资产。批次只尝试一次，失败保留且要求显式重试。进程意外退出使用 BullMQ 的有限 stalled 恢复，完成项已存入数据库，重入时只选缺失指纹。管理员暂停状态在重启后保留；正常结束和失败均保留本批计数、字节及安全错误码，不记录私人路径。批次完成日志增加 elapsedMs 和 concurrency，供实际运行验证速度。文件读取前后校验大小、mtime 和 inode，数据库按原路径与 updateId 条件更新，拒绝删除、扫描和其他任务产生的过期快照。

持续模式与批次上限按库保存在 Redis；API 或后台进程重启后仍能接续，管理员暂停状态不会被自动恢复。全库就绪后关闭接续，不自动追踪以后新增的文件，也不自动开启手机上传。协调器与管理员命令共用独立 PostgreSQL advisory lock，串行替换已完成任务，防止多个实例误删另一实例刚创建的新批次。后台定时检查与完成事件解耦，失败任务始终保留；重试仍需明确管理员操作。Redis 控制数据使用现有队列存储的持久化与备份策略，不新增存储服务。

管理接口为 `GET/PUT /api/admin/fork/iphone-backup`，分别要求管理员及 `queue.read` / `queue.update` 权限。PUT 接收 `command: start|continue|pause|resume|retry` 和可选 `limit: 1..1000`；continue 显式开启持续模式，start 停止后续自动接续并提交单批，resume 保留原有模式。已排队或执行中的同 ID 批次不会被重复启动或重置。响应的 continuous 表示仍有待处理照片的持续模式。请求不能指定库或路径，也不能开启手机上传。此 Fork 专用控制器显式排除在官方 OpenAPI 生成链路之外，由 Web 管理页的独立客户端调用；不修改官方 SDK 或移动端。原有官方 HTTP 接口和响应结构不变，无新增数据库迁移。回退到只支持手动批次的版本前应先暂停该队列，既有指纹保留。

此次进度功能已在独立 PostgreSQL、Valkey 与合成文件上验证 14 项集成场景：统计不启动任务、并发启动去重、批次数量上限、暂停跨重启保留、文件之间暂停、显式失败重试、读取预算、超大文件拒绝、文件或资产变化时拒绝过期指纹，以及真实冷却与自动接续、持续模式跨进程重启保留、失败不自动重试和多实例协调。页面的实际 iPhone 本地匹配结果仍需在手机上验收。

### 2026-11-03 读取速度诊断

基线代码为 b556393f338e，NAS 为 i7-1165G7、约 23 GiB 内存，原片位于单盘 HDD 加 119 GiB SATA SSD 缓存的卷，PostgreSQL 位于 NVMe 卷。当时完整批次每 1,000 张约 6～7 分钟，约 6 GiB 原片；5 秒批间冷却占比较小。暂停匹配任务后，24 张真实图片的阶段测量共读取 180,161,749 字节：总耗时 4.031 秒，其中原片内容指纹 3.778 秒、数据库更新 0.140 秒；进程 CPU 0.910 秒，峰值 RSS 237,612 KiB，实际设备读取 339,525,632 字节，缓存状态未控制。

随后对固定的 24 个样本、457,429,200 字节执行只读微基准，覆盖 JPG、JPEG、HEIC、PNG、DNG、NEF、MOV、MP4、INSP、INSV、GIF、TIF，各 2 个文件。先完整预读一次；每轮仅用 vmtouch 驱逐这些样本的 OS 页缓存，不清空全机缓存。NAS SSD 缓存未清空，其内部命中率未控制；采用 ABBA 顺序交替对照，所有轮次逐文件校验相同 SHA-1。样本清单、原始计数与 I/O 记录保存在 NAS 私有部署目录，不提交照片路径或内容。

64 KiB 与 1 MiB 缓冲区的 ABBA 对照未显示更大缓冲区有收益，因此保留既有 64 KiB 实现。保持相同缓冲区后，对单文件读取和两文件并行执行另一组 ABBA：单文件两轮耗时 4.431 / 4.187 秒，两文件并行 2.449 / 1.616 秒，合并样本读取吞吐约提升 2.12 倍。单文件 P50 为 80.5～97.0 毫秒、P95 为 608～686 毫秒；两文件 P50 为 99.7～118.0 毫秒、P95 为 324～653 毫秒。每轮 CPU 分别为 1.301～1.404 秒与 1.098～1.194 秒；峰值 RSS 为 231,896～238,180 KiB 与 235,424～239,868 KiB；实际设备读取约 557.7～558.0 MB，逻辑读取约 457.5 MB。该结果只代表这组缓存条件下的原片读取阶段，不代表全库或含数据库写入的固定提速承诺。

本次仅为补算增加可回退的 1/2 文件并发配置，不调整其他队列或 NAS SSD 缓存策略。双文件模式新增 5 项隔离集成测试，验证真实并行与内容正确性、合计字节预算、暂停只结束在途文件、一失败一成功的准确计数及显式重试、单文件批次上限，共 19 项集成测试通过。回退时先暂停匹配，将并发配置改为 1 并重启，再恢复持续准备；无需回滚数据库或改动原片。

## 本地优先查看与离线验证

官方客户端已经按 checksum 关联远端和本地资产。新内容指纹通过原有同步接口下发，列表和资产详情使用一致的匹配值，手机不需要安装定制版。

在手机设置的高级选项中关闭“优先使用远程图片”。待本地与远端索引准备完成后，选择一张本机确实保存完整原片、未经过 Immich 编辑的匹配照片，断开 NAS 网络并打开大图，应能走本地图片加载器，而非仅显示远端缩略图或 ThumbHash 占位图。只在 iCloud 中、尚未下载到手机的原片不满足此验证起始条件。

这项体验仍需在实际官方 iPhone 客户端上验收；服务端集成测试只能验证下发的内容指纹和关联数据，不能替代 iOS PhotoKit 行为验证。

## 回归验收日志

验收前在 API 和后台进程启用 `IMMICH_FORK_IPHONE_BACKUP_AUDIT=true`，通过 `IphoneBackupAudit` 前缀查找结构化事件。记录测试起止时间；按 `uploadId` 串联同次接收，按 `assetId` 串联已有云端资产。新增事件只记录不透明 ID、字节数和结果，不记录原片名、目录、完整内容哈希或 EXIF。

| 事件 | 能证明什么 |
| --- | --- |
| `fingerprint_ready` | 对应外部资产的内容指纹已经写入数据库 |
| `sync_asset_sent` | 对应资产已写入同步响应流；不代表手机已接收并完成本地关联 |
| `upload_stream_started` / `upload_stream_failed` | 原片流已进入应用，或流失败时应用已读到的原片字节数 |
| `upload_received` | 原片已完整接收，包含实际原片和 XMP 字节数 |
| `duplicate_after_receive` | 原片完整上传后判重，复用已有资产并清理本次暂存副本；这不算“没有上传” |
| `header_duplicate` | 上传请求头命中已有资产，应用未解析原片；不能据此断言代理或网络未接收请求体 |
| `upload_precheck` | 指纹预检的检查数和重复数；不代表客户端最终执行了跳过 |
| `external_asset_created` | 新建了外部库资产，原子发布路径未覆盖已有文件，记录 `overwrite=false` |
| `filename_collision` / `upload_rolled_back` | 重名后尝试追加序号，或失败后清理本次已发布副本 |

手机在本地比较后直接跳过的照片没有上传请求，服务端不能为此虚构逐照片的 `client_skipped` 事件。验证需要组合证据：选一张云端与手机内容一致的照片和一张仅在手机的新照片；确认指纹就绪、手机远端同步与本地哈希完成；在固定测试窗口观察手机备份统计、新照片成功上传的日志、已有照片是否出现“上传后判重”，以及对应云端资产数、原片大小和 SHA-256 前后是否变化。若需要直接证明客户端针对某张照片作出的跳过决定，还需要手机本地索引或客户端日志；单靠服务端“没有日志”不够。

所有字节字段都是应用解析的文件数据，不是设备总网络流量或反向代理接收量。iCloud 下载、缩略图请求和同步索引流量应与向 NAS 上传原片的流量分开。

## 验收与回退

验收应覆盖首次备份、重复与并发上传、同秒重名、库扫描后无第二条资产、用户隔离、无 EXIF 时间回退、离线文件撤销匹配以及 NAS 永久删除后允许重新上传的已接受限制。记录实际新增文件数和客户端上传流量，不能仅依据数据库没有重复行判断没有重复传输。

本次本地检查（包含验收日志补充）：349 项定向单测、40 项数据库与文件系统集成测试通过；TypeScript 检查、ESLint、Prettier、Nest 构建及 108 项迁移顺序与历史保留检查通过。额外运行的既有外部库集成套件有 3 项因缺少 `glarus.nef` 样本失败，不能记为全套通过。EXIF 时间在新增集成测试中使用可控标签，真实 iPhone、HEIC/视频元数据、离线 PhotoKit 显示及生产图库吞吐量仍未实测。

目标文件系统需要支持硬链接，以便完整复制后原子发布且不覆盖现有文件；不支持时上传失败，不降级为覆盖写入。Fork 既有的 INSV 和大于 3 GiB 视频扫描延后策略保持不变，这些尚未建档的既有文件不在首次指纹补算覆盖范围内。

移除目标库环境配置并重启服务可停止新上传路由，已有外部文件不移动、不转换归属。已保存的内容指纹继续用于已有资产的客户端匹配；回退到旧服务端版本时仍保留原有路径 checksum。数据库 down 迁移会删除新增指纹及索引，但不会移回或删除已归档文件；生产回退也需要单独评审。
