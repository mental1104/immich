# HLS 实时转码优化实验（2026-10-19）

## 目的与变更

基于 Pocket 3 4K60 实测中 FFmpeg 启动/首片约 0.5–0.7 秒，以及画质切换时同一会话启动两个 FFmpeg 的现象，验证两项小改动：

1. QSV 解码与 `scale_qsv` 的 `async_depth` 从固定 4 改为：仅 `lowLatency` HLS 用 1，普通转码仍为 4。
2. 只有首次播放尚无活动档位时才由媒体播放列表预热。切换画质时等客户端发出 init/媒体分片请求后再启动转码，避免用播放位置提示先启动、随后又因客户端实际分片位置不同而重启。

当前代码基线为分支 `nas-dev-x5-jpg` 上的 `4e0c9786974df72c6e618bcdf200edca002f6050`；其中 HLS 服务代码与 Server 镜像 `nas-dev-bce7ce7274a7` 的代码相同。实验镜像分别为 `immich-server:nas-dev-hls-qsv-depth1-exp`（仅第 1 项）与 `immich-server:nas-dev-hls-opt2-exp`（两项），均只在 `immich-hls-test` 使用。组合候选镜像 ID 为 `sha256:64b653ec34c1d3ce154849bf22cfadddd1c2944a9e534d466537fab1092ffdec`。测试期间生产容器未修改。

## 首帧 A/B

同一 Pocket 3 原片、NVMe HLS 目录、QSV、1080p H.264、相同测试图库和 Chromium/Hls.js；每组 3 次预热 + 20 次新会话有效样本，无 fatal error。4 组在相邻时段运行，测试 API 与网络路径不变；OS 页缓存未清除。单位为毫秒，百分位使用 nearest-rank。

| 网络 | QSV 队列 | P50 | P90 | P95 | 最大 | 有效样本 | 失败 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| LAN | 4（基线） | 613.8 | 628.3 | 628.8 | 628.9 | 20 | 0 |
| LAN | 1（候选） | 560.7 | 576.5 | 577.0 | 577.8 | 20 | 0 |
| 3 MB/s 总限速 | 4（基线） | 826.8 | 844.5 | 844.7 | 858.6 | 20 | 0 |
| 3 MB/s 总限速 | 1（候选） | 769.8 | 790.7 | 793.5 | 798.9 | 20 | 0 |

队列深度 1 的 P50/P95：LAN 快 53.1/51.8 ms；3 MB/s 快 57.0/51.2 ms。对应资源计时也显示首个 `init.mp4` 中位耗时 LAN 532.6→482.1 ms、限速 543.5→482.6 ms；`seg_0.m4s` LAN 519.5→469.0 ms、限速 740.3→681.4 ms。结论是稳定的小幅（约 50–60 ms）改善，不是数量级变化。

## 连续转码与播放

比较相同 60 秒媒体产出日志：队列 4 为 19.716 秒（3.043×），队列 1 为 19.833 秒（3.025×），相差约 0.6%，没有观察到明显吞吐损失。两者都显著高于 1.3×目标。

队列 1 候选在 3 MB/s 总限速下连续播放：首帧 924.5 ms；视频媒体时间到 60.013 秒，buffered 覆盖 `[0, 62.08]`；无首帧后的 `waiting`/`stalled`，无 fatal Hls.js 错误。限速配置为共享令牌桶 3,000,000 B/s、64,000 B 突发；这是链路限速，不包含 RTT/抖动/丢包。

## 画质切换与 Seek

使用同一 Hls.js 测试页，在 3 MB/s 链路上 Seek 到 5/30/50 秒并快速双 Seek，然后从 1080p 切至 720p。改动前后各 1 次，数据仅作诊断，不代表可靠百分位。

| 指标 | 队列 1、旧预热行为 | 队列 1、跳过切档预热 |
| --- | ---: | ---: |
| Seek 5 秒 | 810.8 ms | 811.5 ms |
| Seek 30 秒 | 1,090.6 ms | 1,096.4 ms |
| Seek 50 秒 | 1,038.4 ms | 1,015.6 ms |
| 快速 30→50 秒 | 293.5 ms | 283.2 ms |
| 切档命令到 `playing` | 868.7 ms | 920.8 ms |
| 切档 `waiting`→`playing` | 633.0 ms | 687.3 ms |
| 新 720p 档 FFmpeg 启动数 | 2 | 1 |

日志显示旧逻辑先为提示位置 53 启动进程，客户端随后实际请求更早的第 49 段，导致第二次初始化。跳过档位切换预热后，实际请求只启动第 49 段一次，少启动一个 FFmpeg。切档恢复耗时没有显示改善；本次单样本反而多约 54 ms，样本量不足以判断该差别是否真实。测试中仍出现 aborted 请求及一个可恢复的非 fatal `bufferStalledError`，没有 fatal 错误。

## 兼容性、验证与限制

- HTTP 路径、方法、响应、鉴权、HLS playlist schema 均未更改；移动端和 SDK 未修改。
- `HLS` 单测更新了档位切换行为断言；HLS/转码/媒体三个目标测试文件共 292 项通过。全量 Server 单测 107 个测试文件通过，2,360 项通过、1 项预期失败（总计 2,361 项，约 49 秒）；目标 TypeScript 文件的 Prettier 与 ESLint 检查通过，实验镜像构建成功。
- 实际 HLS FFmpeg 日志确认 `-async_depth 1` 与 `scale_qsv:async_depth=1`；普通转码行为保持 4，并由媒体服务测试覆盖。
- 浏览器指标来自 Chromium `<video>` 与 `requestVideoFrameCallback`，不是完整登录后的官方 Immich Web UI 或物理显示首帧。画质切换只有一组前后样本；建议完整 Web UI 和多个 Pocket 3 片段再复核。
- 本节指标来自隔离环境，不代表生产验证。回退 HLS 改动只需恢复 `getAsyncDepth()` 对低延迟场景返回 4，并恢复 `prewarmVariant()` 在档位变化时的预热分支。

## 结论与部署状态

本轮可确认的收益是首帧中位数约快 50–60 ms，持续转码约 3.0×，3 MB/s 链路下该测试片段连续 60 秒未观察到首帧后的卡顿；切档路径则确认少启动一个 FFmpeg，但单样本没有证明切档延迟下降。因此，这些改动是可测的小幅首帧优化和避免重复启动的正确性/资源改进，尚不能称为达到 3 秒/5 秒目标的重大提升。

性能组是当前 HLS 代码（相对本轮实验基线）与 HDD/SSD 的既有基准背景，不包含对原始 `7b13d900` worktree 的完整 20 次 A 组复测；因此本报告不把它描述成完整 A/B/C 结论。原始逐次记录在随附脱敏 CSV 中。

全量测试完成后，隔离测试 Server 已恢复到 HEAD 镜像 `immich-server:nas-dev-bce7ce7274a7`，仍使用开发 SSD HLS 目录和只读样本挂载；实验 API key 已从隔离数据库删除，限速代理已停止。实验期间生产 Immich、生产数据库/Valkey、生产 HLS 目录均未改动。之后按用户要求，将当前代码部署到生产 Server，镜像为 `immich-server:nas-prod-hls-web-hevc-search-4e0c9786974d-1fcb7ae4`；生产 API 健康检查返回 `pong`。该部署还包含中文查询改走描述字段匹配的搜索逻辑。回退 HLS 源码只需恢复 `server/src/utils/media.ts` 和 `server/src/services/hls.service.ts` 的改动，并同步恢复对应测试断言；搜索逻辑则恢复 `server/src/services/search.service.ts` 中的中文分流即可。
